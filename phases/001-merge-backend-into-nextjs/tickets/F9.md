## Decisions

| Question | Answer | Why |
|---|---|---|
| `tdd.md`'s project-structure row for `lib/api.ts` says only "API_URL becomes same-origin (relative prefixUrl, or drop prefixUrl entirely)" — which of the two, concretely? | Neither literally — compute the origin dynamically: `typeof window !== 'undefined' ? window.location.origin : ''`, kept as `ky`'s `prefixUrl`. **Decided autonomously — no human available this session.** | Every existing call site in `lib/api/*.ts` (28 call sites across 8 files, e.g. `api.get('api/categories')`) passes its path **without** a leading slash, because `ky` throws `` `input` must not begin with a slash when using `prefixUrl` `` whenever `prefixUrl` is truthy. Dropping `prefixUrl` entirely (or setting it to `''`) makes `ky` fall through to using that bare relative path as the literal `fetch()` input — which the browser then resolves against the *current document's path*, not the origin. On a nested route like `/settings/account`, `fetch('api/categories')` resolves to `/settings/api/categories`, not `/api/categories` — a real, silent breakage that "drop prefixUrl" would introduce on every page except `/`. `window.location.origin` is an absolute URL, so it reproduces the exact same correct-regardless-of-current-path property the old `http://localhost:4000` absolute value had. The `typeof window` guard is not stylistic: `SessionProvider.tsx` is imported by `app/(app)/layout.tsx`, itself `'use client'` — Next.js App Router still executes `'use client'` module top-level code during SSR to produce the initial HTML, so an unguarded `window.location.origin` at module scope would throw `ReferenceError: window is not defined` on every server-rendered page load. `lib/api.ts` already uses an identical `typeof window === 'undefined'` guard for `getAccessToken`, so this matches the file's own established convention, not a new one. |
| `e2e/auth.spec.ts:21` also hardcodes `http://localhost:4000/api/auth/login` inline (not through `e2e/helpers/api.ts`) — tasks.md's T027 line only names `e2e/helpers/api.ts` and `playwright.config.ts`; is this in scope? | Yes — fix it too, importing `API_URL` from `./helpers/api` instead of a second, independent hardcoded literal. **Decided autonomously — no human available this session.** | T027's own goal (per the TDD and the task note) is that nothing in the retargeted e2e suite still reaches port 4000. Leaving this literal untouched would mean one test keeps talking to `dime-api` even after every other file is retargeted — exactly the kind of half-cutover T028's "kill dime-api and re-run" step exists to catch. Fixing the real dependency here is cheaper and more honest than discovering it only when the standalone run fails. |
| `LEARNINGS.md` flags `e2e/categories.spec.ts:50`'s `expect(body.error).toMatch(/used/i)` as assuming the old flat error shape, explicitly deferred to "`T027`, after auth is ported" — is fixing it part of this ticket? | Yes — `expect(body.error.message).toMatch(/used/i)`, since `body.error` is now the structured `{code, message}` object once this route runs through `dime-web`'s own standardized envelope. **Decided autonomously — no human available this session.** | `LEARNINGS.md` names this fix as T027's job by name ("recorded here now so the fix isn't rediscovered from a red CI run later") — this is reading a decision already made for me, not inventing a new one, but it's listed here because the task line in `tasks.md` doesn't itself name the file. |
| What same-origin value does `e2e/helpers/api.ts`'s `API_URL` become? | `http://localhost:3000` | Matches `playwright.config.ts`'s existing `use.baseURL` and the one remaining `webServer` entry (the `dime-web` one) after the `dime-api` entry is dropped. |
| How to actually prove the standalone cutover for T028 (the task says "kill it… or otherwise confirm nothing… still reaches port 4000") | Kill it — find the process bound to `:4000` via `lsof -i :4000`, stop it, then re-run the full Playwright suite | The task's own text treats "confirm nothing reaches :4000" as the weaker fallback ("or otherwise confirm") when killing isn't possible; killing is possible here (the process is a local `dime-api` dev server owned by this session's operator, explicitly said to be freely restartable per `AGENTS.md`'s "Where the app runs locally" row: "Nothing must stay running between sessions; both are freely restartable"), and it's strictly stronger evidence than a static grep — a grep can miss a dynamically-built URL, a live 4xx/5xx from a dead port cannot lie. |

Diff read closely against `references/review.md`'s correctness/security/convention lenses directly (no
`.claude/agents/reviewer`/`phase-reviewer` definition installed in this repo — `LEARNINGS.md`'s Tooling
section — and this session has no separate subagent-review tool available):

- **Correctness.** `AccountForm.tsx`'s fix reads `body?.error?.message`, matching the live-verified
  `{error:{code:"VALIDATION_ERROR",message:"..."}}` shape exactly (curl transcript below). `lib/api.ts`'s
  and `SessionProvider.tsx`'s `typeof window !== 'undefined' ? window.location.origin : ''` guard is
  necessary, not decorative — confirmed by tracing the actual import chain
  (`app/(app)/layout.tsx` → `'use client'` → still server-rendered by Next.js for the initial HTML →
  `SessionProvider` → `initApiClient`/`lib/api.ts`'s module-scope `ky.create()` call) and by `ky`'s own
  source (`node_modules/ky/distribution/core/Ky.js`: `prefixUrl: String(options.prefixUrl || '')`, and the
  leading-slash-rejection branch only runs when `prefixUrl` is truthy) — every `lib/api/*.ts` call site
  passes its path without a leading slash specifically because of that constraint, so a relative/empty
  `prefixUrl` would silently resolve requests against the current page path rather than the origin.
- **Security.** No secrets, tokens, or user input touched by any of the four diffs. `window.location.origin`
  is the browser's own actual origin, not attacker-influenced input — no open-redirect/host-header-style risk
  introduced.
- **Convention.** `SessionProvider.tsx`'s new constant is a one-line pointer back to `lib/api.ts`'s comment
  rather than repeating the full rationale, matching this codebase's general preference for one canonical
  explanation. Both files already used an identical `typeof window === 'undefined'` guard style elsewhere
  (`lib/api.ts`'s pre-existing `getAccessToken`), so the pattern isn't new to either file.

Nothing required a further code change. One real, non-obvious finding surfaced during T028 (not a defect in
the shipped code — see `LEARNINGS.md`'s new entry): the full Playwright suite, run serially against
`dime-web`'s own rate limiter for the first time ever (every earlier ticket's e2e coverage either targeted
`dime-api` directly or only ran a handful of specs), exhausted the default 100/min single shared bucket
(local runs never set `x-forwarded-for`) and cascaded into ~85 failures whose real cause was a `429` on
`registerTestUser`, not a cutover regression. Fixed by bumping `RATE_LIMIT_MAX` in `.env.local` (gitignored,
local-only, not a code or product change) to the same order of magnitude `tdd.md` already records for
`dime-api`'s own dev environment. After that, the suite passed cleanly — including the standalone run below,
with `dime-api` itself killed.
