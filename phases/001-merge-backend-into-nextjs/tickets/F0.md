# F0 — Foundational: shared plumbing every module needs

**Feature** `../tasks.md#feature-0-foundational--shared-plumbing-every-module-needs` · **Design** `../tdd.md` · **Story** —

## Goal

Add the shared backend plumbing the rest of the `dime-api` → `dime-web` port depends on: Prisma
(schema, migrations, singleton client), a standardized error-response helper, a Postgres-backed rate
limiter, a bearer-JWT auth-verification helper, and a few small copied utilities — plus a defensive
`/health` → `/api/health` rewrite. Nothing product-facing changes: no `app/api/*` route handler exists
after this ticket, and `dime-api` keeps serving the whole app until Feature 1 lands.

## Decisions

| Question | Answer | Why |
|---|---|---|
| Existing uncommitted devx-starter scaffolding sitting on `main` before this ticket started | Committed to `main` first (`chore: add devx-starter scaffolding`, `e2caec8`), branched from a clean `main` | Keeps scaffolding history separate from F0's feature history |
| `errorResponse.ts`'s signature — the TDD self-contradicts: the project-structure line shows `apiError(status, code, message)`, the Architecture table's "Error `code` values" row says `apiError(status, message)` should derive `code` from `status` internally | `apiError(status, code, message)` — explicit `code` param, but typed as the fixed `ErrorCode` union (`'VALIDATION_ERROR' \| 'UNAUTHORIZED' \| 'NOT_FOUND' \| 'CONFLICT' \| 'RATE_LIMITED' \| 'INTERNAL_ERROR'`), not `string` | User's call. The union type still closes the Architecture table's actual concern (no route can invent a free-text code), just via TypeScript rather than internal derivation. `tdd.md`'s Architecture table is corrected to match (see step 5) |
| Copying `DATABASE_URL`/`JWT_ACCESS_SECRET` values from `../dime-api/.env` into `dime-web/.env.local` | Copied directly | Required for this ticket's own done-check (`prisma migrate status` showing zero drift against the shared `dime_dev` database); `.env.local` is already gitignored (`.env*` in `.gitignore`), values are local-only and never committed |
| `authenticate()`'s exact call shape — the TDD says "verifies bearer token via jose, returns `{userId,email}` or throws a typed AuthError" but Fastify's preHandler pattern has no direct Next.js equivalent | Takes the Web `Request` object directly: `authenticate(request: Request): Promise<{userId: string; email: string}>`, throws `AuthError` (extends `Error`, no built-in `status` field — callers map it to `401` via `apiError` themselves) | Matches what's actually available inside a Route Handler; no second reasonable design changes the shape any future route handler calls it with |

## Not verified

- No "running instance" criterion — this ticket ships no `app/api/*` route handler, so there is
  nothing an HTTP request can exercise yet (matches the TDD's own Feature 0 checkpoint: "Nothing
  product-facing yet — no route handler exists"). The first real request-response evidence lands with
  Feature 1's `/api/health` and `/api/categories` routes.
- The `/health` → `/api/health` rewrite (`T008`) is only confirmed by a successful `npm run build`;
  it can't return a real response until `/api/health`'s route handler exists in Feature 1.
- `checkRateLimit`'s Postgres upsert concurrency (`ON CONFLICT ... DO UPDATE`) is asserted by a
  mocked-Prisma unit test, not a real concurrent-request test against Postgres — matches every other
  service-layer test in this port (mocked Prisma, per `tdd.md`'s Testing table).

## Out of scope

- Wiring the rate limiter or `authenticate` helper into any route handler — no route exists in this
  ticket (Feature 1+).
- Any change to `dime-api` itself, or to the frontend's `lib/api.ts`/`SessionProvider.tsx` (Feature 9).
- Resolving the TDD's open questions #1 (Kuberns health-check path) or #2 (real-IP header) — the
  rewrite and `x-forwarded-for` default handle both defensively without needing an answer now.
