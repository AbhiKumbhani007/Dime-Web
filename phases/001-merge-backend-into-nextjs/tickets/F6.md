# F6 — Ledger

**Feature** `../tasks.md#feature-6-ledger` · **Design** `../tdd.md#api-contracts` · **Story** US6

## Goal

Port `dime-api`'s `ledger` module into `dime-web` as Next.js Route Handlers backed by a framework-agnostic
service layer: people CRUD, entries CRUD, and bulk settle-all with its optimistic-concurrency
`expectedBalance` check — the one explicit concurrency guard anywhere in this API. Sixth ported module,
following F1–F5's service/route/test conventions. `dime-api` **is** reachable from this session (confirmed
live at `http://localhost:4000/health`, unlike the F5 session note in `LEARNINGS.md` which was true only in
a different, remote execution environment) — its `src/modules/ledger/*` source is the primary port source,
cross-checked against `dime-web`'s own already-shipped frontend client (`lib/api/ledger.ts`,
`hooks/useLedger.ts`), which already depends on the exact response shapes below in production code.

**Operator override in effect for this ticket, recorded per the operator's explicit instruction:** two
stop-list items fire — this feature touches **money** (ledger balances, settlement amounts) and **a
concurrency primitive** (settle-all's `expectedBalance` optimistic-concurrency check). Per the skill's step
5, both would normally stop the ticket before any code is written for a person to read the plan first, and
per `references/review.md` they'd also select the "three lenses, immediately" review path. This session runs
fully autonomously with no interactive human available — the operator explicitly authorized proceeding past
both stops end-to-end. Continuing to code; the review at the bottom of this spec is the (self-run) substitute
for the three-lens pass step 5 would otherwise have queued up for a person.

## Decisions

| Question | Answer | Why |
|---|---|---|
| `tdd.md`'s contracts table documents `POST /api/ledger/people` → `201 LedgerPerson` (bare), `GET`/`PATCH /api/ledger/people/:id` → bare `LedgerPerson(WithBalance)`, `POST /api/ledger/people/:id/entries` → `201 LedgerEntry` (bare), `PATCH /api/ledger/entries/:id` → `200 LedgerEntry` (bare) | Wrong on all four — every one of these is wrapped: `{person: LedgerPersonDTO}`, `{person}`, `{entry: LedgerEntryDTO, person: LedgerPersonDTO}`, `{entry, person}` respectively | **Decided autonomously — no human available this session.** `dime-api/src/modules/ledger/ledger.routes.ts` (live, reachable this session) shows every one of these `reply.code(...).send({person})` / `send(result)` where `result` is `{entry, person}` or `{person, ...}` — never a bare object. `dime-web`'s own already-shipped `lib/api/ledger.ts` (`createLedgerPerson`, `getLedgerPerson`, `updateLedgerPerson`, `createLedgerEntry`, `updateLedgerEntry`) is independently typed against these exact wrapped shapes in production code already. Same "documented as bare, actually wrapped" correction class F1 (categories), F2 (transactions), F3 (budgets), and F4 (templates) each made once for their own module — `LEARNINGS.md` names this as a pattern to check on every remaining row, and this is that check for ledger. Corrected in `tdd.md`'s API contracts table as part of this ticket. |
| `tdd.md`'s settle row names the service function `settleAll` | The actual exported function is `settlePerson` | Same source (`ledger.service.ts`); `settleAll` doesn't exist as a name anywhere in the port source. Corrected in `tdd.md` alongside the envelope fixes above — small, but left uncorrected it would send the next reader searching for a function that isn't there. |
| `tdd.md`'s settle row says `409 (optimistic-concurrency check...)` but doesn't mention the second, unrelated 409 cause | `settlePerson` has **two** distinct 409 triggers: (1) zero active (unsettled) entries to settle at all — `httpError(409, 'No outstanding entries to settle')` — and (2) a supplied `expectedBalance` that doesn't match the current computed balance — `httpError(409, 'This balance changed — reopen the dialog and try again')`. Both are ported and both get their own test | The live source's own code comment calls this out explicitly: *"Both 409s below intentionally share one message class — the client action (reopen the dialog / retry) is identical for either cause."* Dropping the first (no-outstanding-entries) case from the contract table would under-specify a real, already-implemented behavior. |
| How does a route handler turn `settlePerson`'s/`createPerson`'s/`updatePerson`'s `httpError(409, '<specific message>')` into the standardized envelope? | Extend the existing `e.statusCode === 404` pattern every prior route already uses (see `app/api/budgets/route.ts` etc.) with a parallel `e.statusCode === 409` branch, forwarding `e.message` verbatim into `apiError(409, 'CONFLICT', e.message)` | Every prior 409 in this codebase (categories' duplicate name, templates' duplicate label) came from a Prisma `P2002` unique-constraint violation surfaced as a bespoke `{code: 'DUPLICATE_...'}` object with the message hardcoded in the route handler, because the service layer had no message to hand back. Ledger's two 409s are different: they're application-level checks (case-insensitive name collision; balance mismatch) that already throw `httpError(409, '<the exact message the client should show>')`, mirroring the exact same `statusCode`-checking shape every route already uses for 404. Reusing that shape rather than inventing a third pattern (a `{code}` object with a hardcoded route-side string) keeps the two 409 messages defined once, in the service, rather than duplicated into every route that might trigger them. |
| Zod v4: does `z.number().finite('<message>')` (dime-api's exact `SettleBodySchema` line) actually surface that custom message for `Infinity`/`NaN`? | No — confirmed live via `node -e` against the installed `zod@4.3.6`: `z.number()`'s own base type check already rejects `Infinity`/`NaN` before any `.finite()`/`.refine()` runs, always with a generic `"Invalid input: expected number, received Infinity"`-shaped message, regardless of the custom message supplied to `.finite()`. Ported as `expectedBalance: z.number().finite('expectedBalance must be a finite number').optional()` unchanged (the call is harmless, just not the message that actually surfaces) — the *rejection* still happens, only the wording differs from dime-api's v3 behavior | Same class of "v4 default message wins over a v3-authored custom one" as the already-documented `errorMap` and `.min(1, msg)` quirks in `LEARNINGS.md`; this ticket's own service/route tests only assert `success === false` / status `400`, never the exact wording, matching how `common.schema.ts`'s `AmountSchema` test already handles its own equivalent `Number.isFinite` refine (see `budgets.service.test.ts`'s "rejects a non-finite amount" — asserts failure only, not message text). Recorded as a new `LEARNINGS.md` line rather than silently worked around. |

## Not verified

- No `e2e/ledger.spec.ts` exists in this repo today — auth isn't ported until Feature 7, same deferral
  reasoning F1 through F5 each recorded for their own module.
- The exact wording of `expectedBalance`'s `.finite()` validation message under Zod v4 (see Decisions table
  above) — the *rejection* is verified live via `node -e` and by a test asserting `400`, but no test pins the
  literal message text, since v4 doesn't actually surface dime-api's v3-authored custom string for this case.
- Concurrent settle-all requests actually racing at the database level (two real overlapping transactions) —
  covered only by the unit-level 409 checks against a mocked Prisma client, not a true concurrency test
  against Postgres. `prisma.$transaction`'s serialization is relied on, not independently verified under load,
  matching the level of rigor every other ported module's concurrency-adjacent logic (e.g. the rate limiter's
  upsert) was verified at.
