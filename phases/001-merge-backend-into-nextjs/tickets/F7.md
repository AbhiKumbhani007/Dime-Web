# F7 — Auth

**Feature** `../tasks.md#feature-7-auth` · **Design** `../tdd.md#api-contracts` · **Story** US7

## Goal

Rewrite `dime-api`'s `auth` module — the one service coupled to Fastify (`fastify.prisma`/`fastify.jwt`)
rather than a framework-agnostic `prisma` argument — into `dime-web`'s `lib/server/auth/auth.service.ts`,
injecting `prisma` directly and replacing `@fastify/jwt` with `jose`, and implement its 7
`app/api/auth/*` Route Handlers (register, login, refresh, logout, `me` GET/PATCH/DELETE, `me/password`,
google), so `dime-web` can register, log in, refresh, and manage a user's own account entirely on its own
routes. This is the last piece needed before Feature 9 can cut the frontend over to same-origin. Last
product module before F8 (CSV import/export).

## Decisions

| Question | Answer | Why |
|---|---|---|
| `PATCH /api/auth/me/password`'s success body — `tdd.md`'s contract row explicitly leaves this open ("no body, or `{}` — confirm at implementation via the ported service's actual return, which is `void`") | `200 {}` (empty JSON object, no message field) | **Decided autonomously — no human available this session.** `dime-api`'s own route sends a free-text `{message: 'Password updated'}`, but no other endpoint in this codebase's standardized envelope carries a bare human-readable `message` field (see `docs/api.md` — every success body is either a named-key wrapper or, for auth specifically per the contract table, a flat resource). An empty object satisfies the `void` return, needs no new field in the standardized shape, and is one of the two options the TDD's own row explicitly offered. |
| Zod v4 syntax for email validation — `tdd.md` says "Zod v4" but doesn't give the exact API surface for `.email()`, which changed between v3 and v4 | Top-level `z.email('Invalid email format')`, not the deprecated `z.string().email()` | Matches this codebase's already-established convention for the same class of built-in validator: every ported schema uses the non-deprecated top-level form for `cuid` (`z.cuid(...)`, see `categories.schema.ts`, `budgets.schema.ts`, `transactions.schema.ts`), not the deprecated `z.string().cuid()`. `common.schema.ts` is the one holdout still using the deprecated chained form; not touched here since it's out of this feature's scope. |
| Whether the 7 auth routes are subject to the global rate limiter, same as every other module | Yes, all 7, no per-route exemption | Verified against `dime-api`'s **live source** (`dime-api/src/server.ts`): `@fastify/rate-limit` is registered once, globally, before every route module including `authRoutes`, with no per-route `config: {rateLimit: ...}` override anywhere in `auth.routes.ts` (contrast `csv.routes.ts`'s explicit `{max: 10, timeWindow: '1 minute'}` override on export, which is a different, not-yet-ported module). `tdd.md`'s contract table doesn't spell this out per-endpoint for auth the way it does implicitly for every other module via the T005 dependency; reading the live system settles it rather than guessing. |
| Error-status-to-`code` mapping for the service's `httpError(statusCode, message)`-shaped throws (409 register, 401 login/refresh/google, 400 wrong-old-password, 404 unreachable-in-practice paths) | A single, small per-route mapping function translating `statusCode` → the fixed `ErrorCode` enum from `lib/server/errorResponse.ts` (`400→VALIDATION_ERROR`, `401→UNAUTHORIZED`, `404→NOT_FOUND`, `409→CONFLICT`, anything else→`INTERNAL_ERROR`) | `tdd.md`'s Architecture table already fixes this exact enum uniformly for every route handler in the phase; auth's service throws are all `httpError`-shaped (`Error & {statusCode}`), unlike categories' mixed `httpError`/`{code: 'DUPLICATE_NAME'}` throws, so one small mapper suffices instead of per-error-type branching. |
| `GET /api/auth/me` returning `404` when the token's `userId` no longer has a row — `tdd.md`'s contract row for this endpoint lists no error statuses besides the blanket `401` | Ported and kept as a real, reachable path | Not merely defensive: a user who calls `DELETE /api/auth/me` still holds a live access token for up to its 15-minute TTL. A second request with that same token (`GET`/`PATCH /api/auth/me`) legitimately hits "authenticated, but the row is gone." `dime-api`'s `getMe`/`updateMe` already handle this (`getMe` returns `null`→404; `updateMe`'s `prisma.user.update` would throw P2025 which the route maps to `500` today in `dime-api` — ported as the same `500` fallback here, since `updateMe` has no explicit not-found guard in the source to port). |

## Review

**Immediate, three-lens review — spec, correctness, security, concurrently** — per
`.claude/skills/ticket/references/review.md`'s first override: this ticket is squarely on the
authentication/authorisation item of the mandatory list, not merely adjacent to it. This repo has no
`.claude/agents/reviewer` definition installed (`LEARNINGS.md`'s Tooling section) and this session has no
subagent-dispatch tool available, so — as F5 did for its own checkpoint pass — the closest available
substitute was used: one careful self-review pass against the full branch diff (`main...HEAD`, 4 commits,
15 files), run explicitly against all three lenses in turn rather than skipped for lack of a dispatchable
agent.

**Spec lens** (drift from `tdd.md`/this spec): every endpoint's status codes and envelope shape were
live-verified against a running `dime-web` instance (`## Live evidence` above) and match the contract table
as corrected during this ticket (`me/password` → `200 {}`). No endpoint, field, or status code in the
implementation diverges from either document. The one genuinely open contract question (`me/password`'s
body) was resolved and written back to `tdd.md` rather than left implicit in code only.

**Correctness lens:** traced every service function against `dime-api/src/modules/auth/auth.service.ts`
line by line. One real gap was found and fixed before this section was written: `googleAuth`'s
`payload.name ?? null` fallback branch (Google `tokeninfo` response with an `email` but no `name` claim)
had no test — added (`lib/server/auth/auth.service.test.ts`, "creates a new user with name: null..."),
bringing `auth.service.ts` to 100/100/100/100 coverage. Everything else checked out: `deleteMe`'s bare
`prisma.user.delete` works cleanly because every one of `User`'s six relations (`RefreshToken`,
`Category`, `Transaction`, `Budget`, `Template`, `LedgerPerson`/`LedgerEntry`) declares
`onDelete: Cascade` in `prisma/schema.prisma` — confirmed by reading the schema, not assumed, and
live-verified (`DELETE /api/auth/me` succeeded for a user with 18 seeded categories). `refreshTokens`'
rotation and `logoutUser`'s idempotency both match the source exactly and are exercised at both the
service and route level. `updateMe`'s lack of an "at least one field" guard is a faithful port (the
source's `UpdateMeBodySchema` has no such `.refine`, unlike `categories`' equivalent schema) rather than an
oversight — an empty-body `PATCH` is a harmless no-op `prisma.user.update({data: {}})`.

**Security lens:** `authenticate()`'s `algorithms: ['HS256']` pin (already-shipped, unchanged) rules out
alg-confusion. Every route checks the rate limit before touching the service, and `mapAuthError`'s default
branch never leaks an internal error's message in the `500` case (`'An unexpected error occurred'`,
matching every other module's convention). `loginUser`'s identical `'Invalid email or password'` message
for both an unknown email and a wrong password (preserved from `dime-api`) still resists response-body-based
enumeration, though a timing side-channel exists (`bcrypt.compare` only runs on the known-email path) — this
is unchanged, pre-existing `dime-api` behavior, not introduced by this port, and out of scope per this
spec's "port, not redesign" framing; noted here rather than silently passed over. Account deletion cascades
to `RefreshToken`, so a deleted user's other live refresh tokens are invalidated as a side effect — a good
property, not one this ticket had to design for (the schema already had it). The Google `tokeninfo`
integration's known weak spot (no `aud`/client-ID check) is unchanged, already flagged in `tdd.md`, and
explicitly out of scope.

No further issues found. Route-handler-level branch coverage (24–44% branch on the small per-file
`envNumber`/rate-limit-fallback helpers) matches the established pattern of every already-shipped sibling
module almost exactly (`categories/route.ts`: 84.74/63.15 stmts/branch; `templates/route.ts`: 87.5/67.85) —
not a gap introduced here, and not one any prior ticket in this phase treated as worth closing.
