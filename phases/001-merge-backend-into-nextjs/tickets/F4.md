# F4 — Templates

**Feature** `../tasks.md#feature-4-templates` · **Design** `../tdd.md#api-contracts` · **Story** US4

## Goal

Port `dime-api`'s `templates` module into `dime-web` as Next.js Route Handlers backed by a
framework-agnostic service layer, so `dime-web` serves `GET/POST /api/templates` and
`PATCH/DELETE /api/templates/:id` with contract parity to `dime-api` — including the three-way `sort`
query param and category-ownership checks on create/update. Fourth ported module, following
F1/F2's route/service/test conventions.

## Decisions

| Question                                                                                                                                                                                                               | Answer                                                                                       | Why                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tdd.md`'s API contracts table says `POST`/`PATCH /api/templates` return a bare `Template`                                                                                                                             | Wrong — corrected to `{template: Template}` (wrapped)                                        | `dime-api`'s actual source (`templates.routes.ts`: `reply.code(201).send({ template })`, same for PATCH) wraps it, and `dime-web`'s own already-shipped frontend client (`lib/api/templates.ts`, `createTemplate`/`updateTemplate` both typed `Promise<{ template: Template }>`) already depends on that shape in production code. `GET`'s `{templates: Template[]}` was already correct in `tdd.md` (marked live-verified). Identical class of correction to F1's categories fix and F2's transactions fix.      |
| `dime-api`'s schema uses `z.string().cuid(...)` for `categoryId` and the `:id` param — deprecated in the installed Zod v4 (`node_modules/zod/v4/classic/schemas.d.ts:132` marks it `@deprecated Use z.cuid() instead`) | Use top-level `z.cuid('message')`                                                            | Matches the non-deprecated precedent already established in `categories.schema.ts` (F1). The existing `cuidParam()` helper in `common.schema.ts` still uses the deprecated form internally — not used here; `TemplateParamsSchema` is written inline the way `categories.schema.ts` does.                                                                                                                                                                                                                         |
| `dime-api`'s `SortQuerySchema` attaches its custom enum message via v3's `{ errorMap: () => ({ message: '...' }) }`                                                                                                    | Use v4's top-level `{ error: '...' }` option                                                 | Verified directly against the installed `zod@4.3.6` via `node -e`: passing `{errorMap}` to `z.enum` does **not** throw, but the custom message is silently discarded — `safeParse('bogus')` falls back to v4's default `"Invalid option: expected one of ..."`. Passing `{error: '...'}` instead produces the intended message exactly. Same API `AmountSchema` in `common.schema.ts` already uses. Recorded in `LEARNINGS.md` since the silent-discard failure mode is a real trap for the next v3→v4 enum port. |
| `dime-api`'s service throws a bare `httpError(409, 'A template with this label already exists')` on a Prisma `P2002` unique-constraint violation                                                                       | Throw a plain `{code: 'DUPLICATE_LABEL'}` object instead; the route handler owns the message | `categories.service.ts`'s established convention (F1) is a plain `{code}` object for an app-level conflict, with `httpError` reserved for 404s. `DUPLICATE_LABEL` names the actual conflicting field (`Template.label`, not `.name`), reading naturally next to categories' `DUPLICATE_NAME`.                                                                                                                                                                                                                     |
| `dime-api`'s `transactions.service.ts` bumps `Template.usageCount`/`lastUsedAt` on transaction create via `tx.template.updateMany`                                                                                     | Out of scope for F4                                                                          | That bump lives in `lib/server/transactions/transactions.service.ts`'s `createTransaction` (F2's module) — it is transactions' concern, not templates'. `templates.service.ts` has no write path touching `usageCount`/`lastUsedAt` at all. Noted here so a reviewer doesn't expect to find it in this ticket.                                                                                                                                                                                                    |

## Not verified

- `usageCount`/`lastUsedAt` bump on transaction create — owned by F2, not exercised by any test this
  ticket adds.
- Zod v4's _default_ (non-custom) validation message wording differs from the v3-era source; status
  codes, envelopes, and every custom message are unaffected — same note as F1/F2.
- No `e2e/templates.spec.ts` exists in this repo today — auth isn't ported until Feature 7, same
  reasoning as F1/F2's e2e deferral.

## Out of scope

- Any change to `dime-api` itself.
- The `usageCount`/`lastUsedAt` bump on transaction create — Feature 2's job (`transactions.service.ts`).
- The frontend cutover (`lib/api.ts`'s same-origin base URL) — Feature 9. `lib/api/templates.ts`,
  `hooks/useTemplates.ts`, and `app/(app)/settings/templates/page.tsx` already exist and already expect
  this ticket's exact contract, but won't reach `dime-web`'s routes until Feature 9 repoints the base URL.
- Auth routes — Feature 7.

Given the ticket skill's step-5 stop conditions: none of the four fire here (not answering a question I
asked the user, F4 doesn't touch auth/money/migrations/concurrency, no scope surprise emerged, not asked
to stop) — proceeding through implementation without a plan-read pause, matching F1/F2's precedent.
