# F5 — Analytics

**Feature** `../tasks.md#feature-5-analytics` · **Design** `../tdd.md#api-contracts` · **Story** US5

## Goal

Port `dime-api`'s `analytics` module into `dime-web` as read-only Next.js Route Handlers backed by a
framework-agnostic service layer, so `dime-web` serves all six `/api/analytics/*` endpoints — `overview`,
`by-period`, `by-category`, `trends`, `top-days`, `budget-vs-actual` — with contract parity to `dime-api`.
The last of the six reuses budgets' `listBudgets` (Feature 3), not its own aggregation. Fifth ported
module, following F1–F4's service/route/test conventions. No mutation anywhere in this feature.

`dime-api` itself is not reachable from this session (repository scope is `dime-web` only, and no sibling
checkout exists here), so — as for every prior module — the authoritative "live system" for a contract the
TDD leaves vague is `dime-web`'s own already-shipped frontend client (`lib/api/analytics.ts`,
`hooks/useAnalytics.ts`) and its test fixtures, which already depend on the exact shapes below in
production code.

## Decisions

| Question | Answer | Why |
|---|---|---|
| `tdd.md`'s contracts table says `by-period` takes query `bucket(weekly\|monthly\|yearly),from?,to?` | Wrong — the param is named `period`, not `bucket`, and it takes a single reference `date?` plus an optional `categoryId?` filter, not a `from`/`to` range | `lib/api/analytics.ts`'s `getByPeriod(params: {period, date?, categoryId?})` and `hooks/useAnalytics.ts`'s `useAnalyticsByPeriod` are already-shipped production code built against this exact shape; `app/(app)/insights/page.tsx` already calls it this way. Identical class of "TDD documented the wrong shape" correction F1–F4 each made once for their own module — `LEARNINGS.md` already flags this exact row as one to check. |
| `tdd.md` doesn't say what `by-period` returns beyond "series array — shape per `analytics.service.ts`" | A single flat object `{period, labels: string[], income: number[], expense: number[], net: number[], from, to}` — parallel arrays, not an array of per-bucket rows | `lib/api/analytics.ts`'s `ByPeriodResult` type and `__tests__/insights.test.tsx`'s `BY_PERIOD` fixture (consumed directly by `IncomeExpenseBarChart` as `data.labels`/`data.income`/`data.expense`) both show this exact flat shape live in production code. |
| What each `period` buckets into, and how each bucket is labelled | `weekly` → 7 daily buckets, Monday–Sunday, labelled `Mon`…`Sun`; `monthly` → one daily bucket per day of the reference calendar month, labelled by day-of-month (`"1"`…`"31"`); `yearly` → 12 monthly buckets across the reference calendar year, labelled by 3-letter month abbreviation (`Jan`…`Dec`) | `lib/utils/analyticsPeriod.ts:16`'s comment — *"Weeks run Monday–Sunday, matching the API's bucketing"* — plus its own `periodBounds` (week/month/year boundaries) confirm the bucket granularity server-side must match. `insights.test.tsx`'s `BY_PERIOD` fixture live-confirms the weekly label format (`['Mon','Tue',...,'Sun']`) exactly. Monthly/yearly label format has no direct fixture — day-number and 3-letter-month were chosen for consistency with weekly's short style and `TrendsChart.tsx`'s existing `{month:'short'}` formatting convention elsewhere in this codebase. Flagged under *Not verified* below since nothing exercises it against a real client render. |
| `tdd.md`'s `by-category` contract row lists only `from?,to?`, no `isIncome` | Add an optional `isIncome?` boolean query param | `hooks/useAnalytics.ts`'s `useAnalyticsByCategory({from?, to?, isIncome?})` and the insights page's `useAnalyticsByCategory({...range, isIncome: donutIsIncome})` already send it in production. Same optional/no-filter-when-absent treatment as `transactions.service.ts`'s own `isIncome` filter. |
| What `overview`/`by-category`/`top-days` do when `from`/`to` are omitted (`tdd.md` marks both optional but never says) | Unbounded on the missing side while querying (no date filter added — same convention as `transactions.service.ts`'s optional `from`/`to`), but the response echoes concrete ISO bounds (`from` defaults to the Unix epoch, `to` to "now") rather than leaving a gap, since `Overview`'s shipped type has no null slot for either field | The shipped frontend never actually omits these (the insights page always computes a concrete range before querying), so there is no live evidence to match against either way. Epoch/now is the simplest value that is both "unbounded" in effect and satisfies the non-nullable response type without a magic-number window. Flagged under *Not verified*. |
| `top-days` — which transactions count toward a day's "total" | Expenses only (`isIncome: false`) | Matches the panel's own title ("Top spending days") and mirrors `budgets.service.ts`'s `listBudgets`, which also defines "spend" as `isIncome: false` transactions only. |
| `budget-vs-actual`'s per-row shape vs. `listBudgets`'s full `BudgetWithProgress` | Map down to `{budget: {id,name,emoji,type}, allocated, spent, remaining, percent}` — a narrower `budget` sub-object, `allocated` renamed from `amount`, `daysRemaining`/`periodStart`/`periodEnd`/`category`/etc. dropped | `lib/api/analytics.ts`'s `BudgetVsActualRow` type is exactly this narrower shape, already shipped; `tdd.md`'s own row for this endpoint says it "reuses `listBudgets`" for the computation, not for the response shape verbatim. |

## Not verified

- Monthly/yearly `by-period` label format (day-number, 3-letter month abbreviation) — no fixture or live
  render exercises these two periods, only weekly.
- The `from`/`to`-omitted default path on `overview`/`by-category`/`top-days` — the shipped frontend never
  exercises it; covered by a unit test only, not a live request.
- No `e2e/analytics.spec.ts` exists in this repo today — auth isn't ported until Feature 7, same deferral
  reasoning as F1–F4.

One real issue was found and fixed in this branch before opening the PR:

- **`getByCategory`'s category re-fetch wasn't scoped by `userId`**, unlike every other direct `Category`
  query in this codebase (`categories.service.ts`, `budgets.service.ts`'s `assertCategoryOwned`). It was
  safe in practice only because `transactions.service.ts` enforces at write time that a transaction's
  `categoryId` always belongs to that transaction's own user — an implicit cross-module invariant, not a
  defense this query made on its own. Fixed by adding `userId` to the `where` clause, with a test asserting
  the scoping (`lib/server/analytics/analytics.service.test.ts`, "scopes the category lookup by userId").

Everything else came back clean: the bucket/date math in `analytics.period.ts` (Monday-start weeks, month/
year rollover via out-of-range `Date` components, leap-February handling) was hand-verified against actual
`node` output and found correct; every corrected `tdd.md` contract row matches `lib/api/analytics.ts`/
`hooks/useAnalytics.ts` exactly; every route follows the established rate-limit-then-auth-then-validate
pattern with `userId` scoping on every other query; tests assert concrete expected values rather than
tautologies.
